# 线下场馆失物认领网页

一个自托管的「失物招领 / 认领」小系统：工作人员登记物品并核对认领，访客公开浏览、
提交辨认答案并获得**不可猜测的查询凭证**，获选人凭**一次性交还码**完成当面交还。

技术栈：**Python 3.12 标准库（零第三方依赖）+ SQLite + 浏览器页面**。
不使用任何 pip 第三方包，镜像构建无需联网安装依赖。

---

## 功能与权限

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 访客 | 浏览**公开描述**；提交辨认答案 + 联系方式，取得一次性查询凭证；凭凭证只查**本人**进度；获选后凭凭证取得一次性交还码 | 看不到私密辨认特征、他人答案、他人联系方式、物品保管状态明细 |
| 工作人员（口令登录） | 登记物品（公开描述 + 私密辨认特征）、查看全部申请与联系方式、撤下/恢复物品、选定一份认领、**误选改判给同一物品的另一份未获选申请**、**把同物误登记的两条记录合并**、重发交还码、核码登记交还、**核码后发现物品仍在馆内时撤销该次交还登记** | — |

关键业务规则（均由数据库事务保证）：

- **并发确认最多成功一次**：同一物品多个工作人员同时「选定」，只有一份申请获选，
  其余待核对申请自动标记为「未获选」。
- **已撤下 / 已交还物品拒绝新申请**；撤下时未处理申请一并标记未获选。
- **一次性交还码**：8 位数字 + 后台随机签发；获选人凭查询凭证查看；
  工作人员核码成功后物品立即变为「已交还」。
- **重复核码无效**：同一码重复提交、两枚码并发核销，都只能成功一次。
- **过期可重发**：工作人员重发后旧码立即失效（查询页与核码均拒绝旧码）。
- **认领误选可改判**：物品仍保管且尚未交还时，工作人员可在原获选申请页输入
  「同一物品的另一份既有未获选申请 + 必填的更正理由」完成改判：
  原申请立即变为未获选、其全部未核销交还码立即失效，并为新获选人签发一枚新的
  一次性交还码；系统保存含申请双方、理由与时间的**更正记录**供工作人员追溯。
  物品已撤下/已交还、目标不属同一物品、目标非未获选、原申请已非获选或理由为空时
  一律拒绝且不改动任何状态；与重发、撤下、核码或另一改判并发时，只允许一次符合
  条件的状态变更生效。改判仅工作人员可见，访客凭各自查询凭证只能看到本人最新状态
  （新码仅新获选人与工作人员可见）。
- **同物误登记可合并**：同一件失物被误登记为两条记录时，工作人员在**保留物品**
  详情页的「合并重复登记记录」表单指定**并入物品**并填写**必填的合并理由**。
  仅当两条记录**均仍在保管（保管中）且互不相同时**才允许合并；两条**各有一份获选
  申请时拒绝且不改动任何数据**。合并在单个数据库事务内原子完成：
  - 并入物品的**全部认领申请与改判记录归到保留物品**；访客原有的查询凭证继续查询
    **本人**申请（物品描述显示为保留物品）；
  - 合计仅一份获选时，**保留该获选申请及其一次性交还码**（不重发），其余待核对申请
    标记未获选；两条都没有获选时，双方待核对申请保持待核对，仍可正常选定；
  - 并入物品状态变为「已并入」：**从公开列表消失**，访客访问旧详情地址自动跳转到
    保留物品，**不能恢复、不能撤下、不再接受新的认领申请**；
  - 工作人员可在保留物品与旧物品详情页查看**合并理由、保留/并入的原物品与合并时间**；
  - 与选定、改判、撤下、核码或另一合并并发时，均按**提交时的最新状态重新核对**：
    不会产生双获选，合并前已作废（改判/重发作废）的交还码仍不能核销，
    两个合并竞争同一并入物品时只有一个生效。
- **交还登记可撤销**：工作人员核码后发现物品实际仍在馆内时，可在已交还物品
  详情页填写**必填的撤销原因**撤销该次交还登记。仅物品仍为**已交还**、且存在
  属于**当前获选申请**且**尚未撤销**的本次核销记录时允许；在同一事务内物品恢复
  为「保管中」、申请归属与获选状态保持不变、已核销码**永久失效**，并按现有有效期
  规则向该获选人签发一枚新的一次性交还码。工作人员可在物品详情页查看
  **原核销时间、撤销时间与原因**；访客凭原查询凭证只看到本人最新状态与新码，
  **不显示撤销原因**。重复撤销、核销记录与当前获选申请不匹配，或与核码等操作
  并发导致条件变化时一律拒绝且不改动任何数据；恢复后现有改判、合并及核码规则
  照常适用（物品再次交还后可再次撤销）。
- 数据库只存查询凭证与交还码的 **SHA-256 哈希**；交还码另以**认证加密密文**存储，
  仅在「持凭证的获选人查询页 / 工作人员详情页」解密显示；HMAC 密钥保存在数据卷，
  不随镜像分发。

## 所需配置（环境变量）

| 变量 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `STAFF_PASSWORD` | 生产必填 | `change-me` | 工作人员登录口令。使用默认值时容器会打印警告。 |
| `HOST_PORT` | 否 | `8080` | 宿主机映射端口（容器内固定 8080）。 |
| `HANDOVER_CODE_TTL` | 否 | `86400` | 交还码有效期，单位秒（默认 24 小时）。 |
| `LF_DATA_DIR` | 一般无需改 | `/data` | SQLite 数据库与密钥目录（Docker 卷挂载点）。 |

## 一条命令启动

```bash
# 可选：复制并修改配置
cp .env.example .env
#   编辑 .env，把 STAFF_PASSWORD 改成强口令

docker compose up -d --build
```

停止 / 重启 / 查看日志：

```bash
docker compose down          # 停止（数据保留在 Docker 卷 lostfound_data 中）
docker compose restart
docker compose logs -f
```

## 使用流程

1. 工作人员打开 `/staff/login`，输入 `STAFF_PASSWORD` 登录。
2. 在登记台录入物品：**公开描述**（访客可见）与**私密辨认特征**（仅工作人员可见）。
3. 访客在首页看到公开描述，打开物品提交「辨认答案 + 联系方式」，
   页面**仅此一次**显示查询凭证，访客自行保存。
4. 访客在 `/query` 粘贴凭证查看本人状态：待核对 / 已获选 / 未获选。
5. 工作人员在物品详情页比对答案与私密特征，点「选定此申请并签发交还码」：
   - 其他待核对申请立即变为「未获选」；
   - 获选人在查询页看到一次性交还码及有效期。
6. 获选人到场出示交还码，工作人员在「核销交还码」页输入 8 位码：
   - 成功 → 物品标记「已交还」，拒绝一切新申请；
   - 重复 / 过期 / 已重发的旧码 → 拒绝并给出原因；
   - 码过期 → 工作人员可在申请详情页「重发新码」，旧码立即失效。
7. **发现认领误选**（物品仍保管、尚未交还）：打开原获选申请页
   （`/staff/claims/{id}`）的「认领误选改判」表单，选择同一物品的另一份
   **未获选**申请并填写更正理由：
   - 原申请变为「未获选」、其交还码立即全部失效；新获选人变为「已获选」并取得新码；
   - 双方凭原有查询凭证只看到本人最新状态，新码仅新获选人与工作人员可见；
   - 改判记录（申请双方、理由、时间）显示在物品详情页，供工作人员追溯；
   - 已撤下 / 已交还、目标非同一物品或非未获选、原申请已非获选、理由为空均拒绝。
8. **发现同一件失物被误登记为两条记录**（两条均仍在保管）：打开要**保留**的那条
   物品详情页（`/staff/items/{id}`），在「合并重复登记记录」表单选择要**并入**的
   另一条记录并填写合并理由：
   - 并入物品的全部申请与改判记录原子归到保留物品，其访客原查询凭证照常查询本人申请；
   - 若两条各有获选申请，合并被拒绝且数据不变；仅一份获选时保留其交还码、
     其余待核对申请标记未获选；都没有获选时待核对申请保留，可继续选定；
   - 并入物品从公开列表消失，访客打开旧地址自动跳到保留物品；该记录不能恢复、
     不能撤下、不再收申请；
   - 合并理由、保留/并入原物品、合并时间显示在两条记录的工作人员详情页供追溯。
9. **发现交还登记有误**（核码后物品实际仍在馆内）：打开已交还物品详情页
   （`/staff/items/{id}`）的「撤销交还登记」表单，填写必填的撤销原因：
   - 物品恢复为「保管中」，原获选人保持获选，已核销码永久失效，
     系统按现有有效期规则为其签发新的一次性交还码；
   - 撤销记录（获选申请、原核销时间、撤销时间、原因）显示在物品详情页，
     仅工作人员可见；访客凭原查询凭证只看到本人最新状态与新码，不显示撤销原因；
   - 物品非已交还、核销记录不属于当前获选申请、该次登记已撤销或原因为空均拒绝；
     与核码等操作并发导致条件变化时同样拒绝且不改动数据；
   - 恢复后改判、合并、核码规则照常适用，物品再次交还后可再次撤销。

## 数据持久化与初始化

- 数据位于 Docker 卷 `lostfound_data`（容器内 `/data`）：
  - `lostfound.db`：SQLite 数据库（WAL 模式）；
  - `secret.key`：会话签名与交还码加密密钥（自动生成，权限 600）。
- 数据库表由 `lostfound/schema.sql` 在容器启动时**幂等初始化 / 升级**
  （`CREATE TABLE IF NOT EXISTS`），不会破坏已有数据。
- 备份：停服后复制卷内 `lostfound.db`（及 `-wal`/`-shm`，或先 `docker compose stop`）。

不使用 Docker 本地运行（需要 Python 3.11+）：

```bash
export LF_DATA_DIR=./data STAFF_PASSWORD=please-change-me PORT=8080
python -m lostfound.init_db
python -m lostfound.app
```

测试（先在本机以 `STAFF_PASSWORD=secret123 PORT=8181 LF_DATA_DIR=/tmp/lfdata`
启动服务，再分别运行；均仅使用标准库）：

```bash
python tests/e2e_test.py       # 端到端 + 并发选定/核码
python tests/rejudge_test.py   # 认领误选改判：改判、拒绝项、追溯、可见性、并发
python tests/merge_test.py     # 同物合并：资格校验、归属/凭证/交还码、追溯、可见性、并发
python tests/revoke_test.py    # 交还撤销：恢复保管/新码/追溯/可见性、拒绝项、并发
python tests/stress_test.py    # 多轮并发选定 / 并发核码压力
```

> 每套测试都会持续写入同一个 `/tmp/lfdata`，请在运行前重启到**空数据目录**；
> 多套连跑时建议每套之间清空数据目录并重启服务。

## 目录结构

```
.
├── Dockerfile                 # 运行环境（python:3.12-slim，无第三方依赖）
├── docker-compose.yml         # 一条命令启动 + 数据卷 + 健康检查
├── docker/entrypoint.sh       # 启动前初始化数据库
├── .env.example               # 配置模板
└── lostfound/
    ├── app.py                 # WSGI 应用 / HTTP 服务 / 路由 / 会话 / CSRF
    ├── db.py                  # SQLite 连接、WAL、IMMEDIATE 事务
    ├── repository.py          # 数据访问与并发安全的业务事务
    ├── security.py            # 随机凭证、哈希、签名 Cookie、AEAD 加解密
    ├── render.py              # 页面渲染（全部动态值 HTML 转义）
    ├── schema.sql             # 建表脚本（幂等）
    └── init_db.py             # 数据初始化入口
```
